C. `repository/PlayerRepository.java` & `TeamRepository.java` (Pessimistic Locking)
--------------------------------------------------------------------------------
- Code Implementation:
  ```java
  @Lock(LockModeType.PESSIMISTIC_WRITE)
  @Query("SELECT p FROM Player p WHERE p.id = :id")
  Optional<Player> findByIdForUpdate(@Param("id") Long id);
  ```
- What Happens at the SQL Level:
  Hibernate translates this directly into a native SQL statement:
  `SELECT id, name, status, base_price FROM players WHERE id = ? FOR UPDATE;`
- This puts an exclusive write lock on that specific row in InnoDB until the transaction commits.

D. `service/BidService.java` (The Algorithmic Heart)
--------------------------------------------------------------------------------
- Method: `placeBid(PlaceBidRequest request)`
- Transactional Logic Flow:
  1. `@Transactional`: Opens a database transaction boundary.
  2. Acquires row locks:
     `Player player = playerRepository.findByIdForUpdate(request.getPlayerId()).orElseThrow(...);`
     `Team team = teamRepository.findByIdForUpdate(request.getTeamId()).orElseThrow(...);`
  3. Validation 1 (Player Status): Ensures player is not already `SOLD`.
  4. Validation 2 (Base Price Floor):
     `if (request.getAmount().compareTo(player.getBasePrice()) < 0) throw new RuntimeException("Bid cannot be below base price");`
  5. Validation 3 (Purse Balance Check):
     `if (team.getBudget().compareTo(request.getAmount()) < 0) throw new RuntimeException("Insufficient budget to place bid");`
  6. Validation 4 (Anti-Self Outbid & Increment):
     `Optional<Bid> highestBidOpt = bidRepository.findTopByPlayerIdOrderByAmountDesc(player.getId());`
     `if (highestBidOpt.isPresent()) {`
     `    Bid highestBid = highestBidOpt.get();`
     `    if (highestBid.getTeam().getId().equals(team.getId())) throw new RuntimeException("You already hold the highest bid!");`
     `    if (request.getAmount().compareTo(highestBid.getAmount()) <= 0) throw new RuntimeException("Bid must be strictly higher than current bid");`
     `}`
  7. Persistence:
     Creates `Bid bid = new Bid(player, team, request.getAmount(), LocalDateTime.now());`
     `bidRepository.save(bid);`
  8. Broadcast:
     `messagingTemplate.convertAndSend("/topic/bids", new BidEventResponse(bid));`

4. CONCURRENCY LOCKING DEEP-DIVE (PESSIMISTIC VS OPTIMISTIC LOCKING)
================================================================================

Why Pessimistic Locking over Optimistic Locking?

1. Optimistic Locking (@Version):
   - Uses a version column. If two threads read version 1 and both try to update, the 
     second thread gets an `OptimisticLockException` and is aborted.
   - In live bidding, 10 franchise owners click simultaneously. If 9 out of 10 users 
     receive an immediate error screen, the user experience is catastrophic.

2. Pessimistic Write Locking (SELECT ... FOR UPDATE):
   - Serializes incoming requests at the database engine level.
   - Thread A locks the row, validates, updates the bid to ₹10 Cr, and commits.
   - Thread B immediately acquires the lock, reads the NEW price (₹10 Cr), determines if 
     its proposed bid (₹10.5 Cr) is higher, updates, and commits.
   - Result: 100% data integrity with zero lost updates and zero false aborts.

6. COMPLETE TECHNICAL DEFENSE (WHY WE CHOSE THIS STACK)
================================================================================

- Why `BigDecimal` instead of `double` or `float`?
  * IEEE 754 floating-point numbers represent numbers in binary fractions. Performing 
    `100.00 - 15.20` in double produces `84.80000000000001`. For multi-crore auction 
    finances, `BigDecimal` provides arbitrary decimal precision with exact rounding modes.
- Why STOMP protocol over raw WebSockets?
  * Raw WebSockets only transfer plain strings or byte arrays without routing headers. 
    STOMP adds a pub-sub frame structure (CONNECT, SUBSCRIBE, SEND, MESSAGE) allowing 
    us to route updates cleanly to `/topic/bids` and `/topic/players`.

7. EXHAUSTIVE MENTOR Q&A / VIVA DEFENSE PREPARATION
================================================================================

Q1: What is a Race Condition in live bidding and how does your code prevent it?
Answer:
"A race condition occurs when two transactions read the same initial state (e.g., current bid = ₹2 Cr), 
both compute a new bid, and both write back simultaneously, causing one bid to overwrite the other 
(Lost Update). We prevent this using Pessimistic Write Locking (`SELECT ... FOR UPDATE`). MySQL locks 
the player row for the duration of the transaction, forcing concurrent bids into a strict, serialized FIFO queue."

Q2: What is the difference between `@Lock(LockModeType.PESSIMISTIC_READ)` and `PESSIMISTIC_WRITE`?
Answer:
"`PESSIMISTIC_READ` (Shared Lock) allows other transactions to read the row but prevents writes. 
`PESSIMISTIC_WRITE` (Exclusive Lock) prevents other transactions from both reading (with lock) and writing. 
We use `PESSIMISTIC_WRITE` because placing a bid modifies the player's active price and creates new bid records, 
requiring exclusive isolation."

Q3: What indexes did you create and why?
Answer:
"In `schema.sql`, we created a composite index on `bids(player_id, amount DESC)`. When retrieving the 
active highest bid, the database can resolve `SELECT * FROM bids WHERE player_id = ? ORDER BY amount DESC LIMIT 1` 
directly via index B-Tree traversal in O(log N) time without performing a full table scan."

Q4: How do you prevent self-outbidding in code?
Answer:
"In `BidService.placeBid()`, we query `bidRepository.findTopByPlayerIdOrderByAmountDesc(playerId)`. 
If the resulting bid exists and `highestBid.getTeam().getId().equals(request.getTeamId())`, we immediately 
throw a `RuntimeException('You already hold the highest bid!')` before persisting any data."
