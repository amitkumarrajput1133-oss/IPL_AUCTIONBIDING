4. YOUR EXACT CODE FILES & WHAT THEY DO
--------------------------------------------------------------------------------
📍 IplAuctionApplication.java
   - The Spring Boot entry point containing the main() bootstrap method.

📍 controller/TeamController.java (/api/teams)
   - GET /api/teams -> Returns all 10 registered IPL franchises.
   - GET /api/teams/{id} -> Returns a specific franchise by ID.
   - POST /api/teams -> Creates a new franchise with starting budget (e.g. ₹100 Cr).
   - PUT /api/teams/{id} -> Updates franchise details (name, shortName, budget, logo).
   - DELETE /api/teams/{id} -> Removes a franchise from the database.

📍 service/TeamService.java
   - Implements team business logic and ensures valid budget allocations.

📍 controller/PlayerController.java (/api/players)
   - GET /api/players -> Returns the full player catalog.
   - GET /api/players/{id} -> Returns a single player's details.
   - POST /api/players -> Adds a new player to the auction pool (defaults to UNSOLD).
   - PUT /api/players/{id} -> Updates player metadata (role, base price, country).
   - DELETE /api/players/{id} -> Deletes a player from the auction registry.
   - PUT /api/players/{id}/sell -> Sells a player to a team, validates JWT role 
     (ADMIN only), verifies squad constraints, deducts purse, and broadcasts to /topic/players.
   - PUT /api/players/{id}/unsold -> Marks player UNSOLD, refunds team purse if previously 
     sold, and broadcasts real-time update to /topic/players.

📍 service/PlayerService.java
   - Implements the core IPL business rules inside @Transactional methods:
     1. Pessimistic read: playerRepository.findByIdForUpdate(playerId) & teamRepository.findByIdForUpdate(teamId).
     2. Budget Check: team.getBudget() >= finalPrice.
     3. Squad Size Check: playerRepository.countByTeamId(teamId) < 25.
     4. Overseas Quota Check: if player.isOverseas(), countByTeamIdAndOverseasTrue(teamId) < 8.
     5. Budget Deduction: team.setBudget(team.getBudget().subtract(finalPrice)).
     6. Status Update: player.setStatus(PlayerStatus.SOLD), player.setTeam(team).
     7. markUnsold(): Handles unsold transitions and automatic budget refunds.

📍 controller/GlobalExceptionHandler.java
   - Centralized @ControllerAdvice that intercepts RuntimeExceptions and validation 
     errors, returning structured JSON error payloads with timestamps, HTTP status, 
     and clean error descriptions instead of 500 stack traces.

📍 dto/SellPlayerRequest.java
   - Data transfer object carrying { "teamId": 1, "finalPrice": 125000000 }.

9. TOP MENTOR QUESTIONS & HOW TO ANSWER CONFIDENTLY
--------------------------------------------------------------------------------
Q1: How do you enforce the 25-player and 8-overseas limits?
Ans: In PlayerService.sellPlayer(), before finalizing the purchase, I execute 
     playerRepository.countByTeamId(teamId) and playerRepository.countByTeamIdAndOverseasTrue(teamId). 
     If the squad size is >= 25, or if an overseas player is signed when overseasCount is >= 8, 
     the transaction immediately throws a descriptive RuntimeException that rolls back the change.

Q2: Why do you need @ControllerAdvice and GlobalExceptionHandler?
Ans: Without centralized exception handling, unhandled Java exceptions bubble up 
     as raw HTTP 500 internal server errors with lengthy stack traces. With 
     @ControllerAdvice, we intercept exceptions globally and return clean JSON containing 
     HTTP status code, timestamp, and a human-readable error message.

Q3: What happens to a team's budget when a player is marked UNSOLD after being sold?
Ans: In PlayerService.markUnsold(), if the player had previously been marked as SOLD, 
     the method retrieves the buyer team, refunds the purchase price back to the team's 
     purse (team.setBudget(budget + price)), disassociates the team, and resets the player's 
     base price to originalBasePrice.

Q4: Why are service methods annotated with @Transactional?
Ans: Selling a player requires updating two database tables: the player table (status, 
     assigned team) and the team table (purse deduction). @Transactional ensures that 
     both updates occur as a single atomic unit of work—if any part fails, all changes 
     are rolled back to prevent data inconsistency.
