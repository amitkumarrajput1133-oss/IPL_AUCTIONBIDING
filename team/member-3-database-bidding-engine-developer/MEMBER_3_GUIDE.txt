4. YOUR EXACT CODE FILES & WHAT THEY DO
--------------------------------------------------------------------------------
📍 schema.sql
   - Complete production DDL script defining tables: users, teams, players, bids, auctions.
   - Sets up primary keys, foreign key constraints, indexes on player_id and amount, 
     and seeds sample marquee players.

📍 docker-compose.yml
   - Multi-container configuration provisioning a persistent MySQL 8.0 instance on port 3306 
     with environment variables (MYSQL_DATABASE=ipl_auction_db, MYSQL_ROOT_PASSWORD=root).

📍 model/ (User.java, Team.java, Player.java, Bid.java, Auction.java)
   - JPA entity mappings using @Entity, @Table, @Id, @GeneratedValue, @Column.
   - Financial columns (budget, basePrice, amount) mapped to java.math.BigDecimal.
   - Relational associations (@ManyToOne, @OneToMany, @JoinColumn).

📍 repository/PlayerRepository.java & TeamRepository.java
   - Employs JPA Pessimistic Locking:
     @Lock(LockModeType.PESSIMISTIC_WRITE)
     @Query("SELECT p FROM Player p WHERE p.id = :id")
     Optional<Player> findByIdForUpdate(@Param("id") Long id);
   - Instructs MySQL to issue a native "SELECT ... FOR UPDATE" query, locking the row.

📍 repository/BidRepository.java
   - Query method: findByPlayerIdOrderByAmountDesc(Long playerId) to fetch the leading bid.

📍 service/BidService.java
   - The algorithmic heart of the auction:
     1. Acquires Pessimistic Write Locks on Player and Team entities within a @Transactional method.
     2. Validates Team Purse: team.getBudget().compareTo(amount) >= 0.
     3. Validates Anti-Self Outbid: Rejects consecutive bids by the same franchise.
     4. Validates Increments: amount.compareTo(highestBid.getAmount()) > 0.
     5. Validates Base Price Floor: amount.compareTo(player.getBasePrice()) >= 0.
     6. Persists new Bid record and updates player's current leading price.

📍 controller/BidController.java (/api/bids)
   - POST /api/bids -> Validates JWT token, prevents franchise impersonation, calls 
     BidService.placeBid(), and broadcasts real-time updates to /topic/bids.
   - GET /api/bids/player/{playerId}/highest -> Retrieves the active leading bid.

📍 config/WebSocketConfig.java
   - Configures STOMP messaging endpoints (/ws-auction) with SockJS fallback and enables 
     simple broker destinations (/topic).

9. TOP MENTOR QUESTIONS & HOW TO ANSWER CONFIDENTLY
--------------------------------------------------------------------------------
Q1: Why did you choose Pessimistic Locking over Optimistic Locking?
Ans: In a fast-paced live auction where 10 team owners click 'Bid' at the same millisecond, 
     Optimistic Locking (versioning) causes 9 out of 10 requests to fail and throw rollback 
     exceptions, ruining user experience. Pessimistic Locking queues requests at the row level 
     in MySQL, allowing the engine to evaluate each bid in strict sequence without failing valid clicks.

Q2: Why did you use BigDecimal instead of double or float for money fields?
Ans: Primitive double and float types use IEEE 754 floating-point arithmetic which causes 
     binary rounding inaccuracies (e.g. 100.0 - 0.2 = 99.80000000000001). For an auction dealing 
     with ₹100 Crore purses, BigDecimal provides arbitrary-precision decimal mathematics to ensure 
     100% financial accuracy.

Q3: How do you prevent a team from bidding on behalf of another team?
Ans: In BidController.placeBid(), we parse the caller's JWT token. If the user's role is 
     TEAM_OWNER and the teamId inside their token does not match the teamId in the PlaceBidRequest 
     payload, the controller rejects the request immediately with an HTTP 403 Forbidden.

Q4: What happens if a team tries to bid higher than its remaining purse?
Ans: In BidService.placeBid(), we compare team.getBudget().compareTo(amount). If the team's 
     current purse is less than the bid amount, a RuntimeException is thrown, rolling back the 
     transaction before any changes are written to the database.
